# Plan: a graph view of a run, and the UI's look

Goal: a run's page can show its steps as a zoomable graph on React Flow,
laid out by dagre, or as the outline it shows today, one at a time by the
reader's choice; and the whole UI takes the look of the two reference
screenshots in `tmp/`, not versioned: a sidebar, a runs table with status
pills, a run page of step cards. Field names in the screenshots are not
ours; the data stays what the manager gives. There is no authentication, so
the profile at the bottom of the sidebar is a placeholder.

Follows [web-ui-plan.md](web-ui-plan.md), which built the UI this changes,
and [contributing/js-dependencies.md](../../contributing/js-dependencies.md),
whose rules the new packages must meet. Each step is one branch stacked on
the one before, checked, reviewed with `review_my_changes.sh <repo>
<previous branch>` until it has no confirmed or plausible finding, then one
signed commit ending in "Generated with Claude Code".

## What exists, for a reader with no memory of it

`ts/neorc-ui/`, React 19, TypeScript 5.9, Vite 8 on Rolldown, Vitest 5 with
Testing Library on jsdom, TanStack Query 5. Hash routing of our own in
`src/router.ts` (`#/runs`, `#/runs/<id>`, `#/flows`, `#/flows/<name>`), which
already parses a query string after the path. Read `ts/neorc-ui/AGENTS.md`
first.

- `src/api.ts`: typed calls on the manager's routes; types come from
  `openapi.json` through `npm run generate` (`Run`, `Task`, `Flow`,
  `Address`, `RunStatus`, `TaskStatus`). A task's `address` is
  `{step, scope: [[container, n], ...]}`, outermost container first; a
  sub-run's `parent_address` names the sub-flow step that started it.
- `src/queries.ts`: the query hooks, the event long poll (`follow`,
  `refresh`), and `useRunTasks`/`useSubRuns`, which poll every 2 s while the
  run is active. Nothing here changes for the graph.
- `src/definition.ts`: `stepsOf(content)` reads a flow definition into
  `StepNode`s: `task` (handler, queue, params, fixedParams), `flow` (the
  sub-flow name, params), `loop` (maxCycles, exitCondition, children),
  `fan_out` (over, children). `instancesOf(container, scope, addresses)`
  gives the iterations or branches a container has been entered with, from
  the addresses of the run's tasks and sub-runs; `addressKey(step, scope)`
  keys them. The graph builds on these two.
- `src/components/RunTree.tsx`: the outline. `published(tasks, subRuns)`
  indexes what the run did by address; `RunTree` recurses over the steps
  with a scope, drawing one section per instance of a container. Keep it.
- `src/components/TaskDetails.tsx`: a task's facts, params, result, error,
  in a `<details>`. The graph's node details can reuse it.
- `src/pages/RunPage.tsx`: the run's facts, `CancelRun` for a root run, the
  tree, the sub-runs table, inputs and output. The view switch goes here.
- `src/index.css`: plain CSS, tokens on `:root`, light and dark by
  `prefers-color-scheme`. No CSS framework, no font files.
- Tests: 60 in Vitest against `src/test/render.tsx`'s `mockApi`, typed
  fixtures in `src/test/fixtures.ts`, and a real recorded run in
  `src/test/word_picker_rounds.json` (2 loop iterations each starting a
  sub-run, a fan-out of 2 branches each with a nested loop of 2 iterations,
  12 tasks), regenerated by `uv run python scripts/record_ui_fixture.py`.
  `python/neorc/tests/test_ui_browser.py` drives the built UI in Chromium
  against a manager on Postgres; it needs `npm run build` first.
- The manager serves `/ui/` with a Content-Security-Policy: scripts and
  connections from its own origin only, styles from it or inline. React Flow
  sets inline styles, which is allowed; it loads nothing from anywhere.
- The bundle is 75 KB gzipped against a budget of 500 KB, checked by the
  build, which also refuses any bundled license outside the allowlist and
  writes `bundled-packages.txt`, committed and checked by CI.

To see it: `examples/hello/README.md` step 1 for a throwaway Postgres, then
`neorc manager start --host 127.0.0.1 --create-schema` with the UI built and
copied to `python/neorc-ui/src/neorc_ui/static/`, a scheduler, a worker per
queue and `neorc flows upload examples/wordplay/flows`; or `npm run dev`
against a manager started with `--no-ui`. `word_picker_rounds` exercises
everything the graph must draw; without a worker on the `scoring` queue its
runs stay active, which is useful for looking at a live one.

| Runtime packages | 2: dagre, graphlib | About 20: `@xyflow/system`, `zustand` 4, `classcat`, d3 drag, zoom, selection, interpolate, transition, color, dispatch, ease, timer, `use-sync-external-store`, and `@types/d3-*` |

| Provenance | None | `@xyflow/react`, `@xyflow/system` and `zustand` yes; classcat and the d3 modules no |

Both are within the rules: licenses allowed, no install scripts, sizes within
budget, versions older than the 10-day cooldown. The gaps to know: dagre and
the d3 modules publish no provenance, and classcat has one maintainer. Elkjs
is not an option, EPL or GPL.

Pin exact versions. Check the cooldown again on the day: `npm view <pkg>
time --json` and take the newest version published 10 or more days before.

## What maps to what

- Sidebar nav: Runs and Flows. "New run" opens the flows list, since a run
  needs a flow; the form stays on the flow's page.
- Pinned workflows: the flows, latest version of each, from `useFlows`.
- Recent runs: the first few of the runs query, with their status dots.
- The profile: a placeholder, an avatar circle with "no account", nothing
  behind it. Authentication has its own plan.
- The no-authentication banner stays, as a slim strip; the plan that
  brought it says the UI says so until authentication lands.
- Stat tiles: nothing in the API aggregates runs. Either drop them, or show
  what the loaded page gives (counts by status among the runs loaded) and
  say so, or add a manager route for counts later. Decide in the step.
- Trigger: nothing in the data. Drop the column.
- Progress per row: tasks finished over tasks published, which needs each
  run's tasks; the list has only runs. Drop it from the table, or add a
  manager route that lists runs with their task counts. Not for this plan
  unless it is cheap on the Postgres side.
- Duration: `created_at` to `finished_at`, as `formatDuration` gives it.
- Run page cards: the tree view, restyled: each step a card, a container a
  card holding cards. The graph view replaces the main column when chosen.
- "Re-run": start a run of the same flow with the same inputs. The form's
  `startRun` does that; a button with a confirmation is small. Optional.
- "Live log": the run's tasks in time order with their started and finished
  times could stand in; or leave the column out. Decide in the step.

### 1. The two packages, and nothing else

One pull request that adds `@xyflow/react` and `@dagrejs/dagre` to
`dependencies` at exact versions, runs `npm ci`, and commits
`package-lock.json` and the `bundled-packages.txt` the build rewrites, which
will list the d3 modules and the rest. The rules say a dependency change is
its own pull request. Import nothing yet.

### 2. The graph: nodes and edges from a run, tested

Pure functions in `src/graph.ts`, no React, tested against the recorded run.

- One node per step instance: each task at its address, each sub-run at its
  parent address, from `published(tasks, subRuns)`. Containers become parent
  nodes, one per iteration or branch from `instancesOf`, nested as the
  definition nests them; React Flow draws children inside a parent when
  `parentId` and `extent: "parent"` are set. A container not entered yet
  gets one parent node marked so, with its children as not published.
- Edges from references: a step's `params` values are references such as
  `tasks.pick_word`, `flows.picker`, `inputs.sentence`, `neorc.item`. An
  edge goes from the step a `tasks.` or `flows.` reference names to the
  step holding the param; `inputs.` and `neorc.` make no edge. One edge from
  every instance the reference resolves to: the consumer's own branch of a
  fan-out it is inside of, every branch or iteration of a container it is
  outside of. Inside a loop, the iterations so far feed a consumer; the graph
  joins its own iteration's and the one before, a chain rather than half a
  square of edges. A fan-out's `over` reference feeds each of its branches.
  The core's rules are in `docs/specs/flows.md`, "Resolving references"; do
  not reimplement resolution, only draw who feeds whom.
- Layout with dagre: nodes sized by their content, rank direction top to
  bottom, compound by laying out each container's children first and
  sizing the parent from them, then the parent's level. Dagre's own
  compound support is weak; nested layouts done by hand are steadier.
- Node data carries what the node shows: name, kind, status, duration, and
  the task or run for the details panel.

### 3. The graph view on React Flow, and the view switch

- `src/components/RunGraph.tsx`: `ReactFlow` with `Controls`, `MiniMap`,
  `Background`, `fitView`, nodes read-only (no dragging into a new layout),
  custom node components for a task, a sub-flow and a container, the status
  badge on each. Clicking a task node opens `TaskDetails` in a side panel;
  a sub-flow node links to its run. The graph re-lays out when the tasks or
  sub-runs query changes, which the active poll drives every 2 s.
- The switch on the run page: a segmented control, "Outline | Graph", the
  choice in the route's query, `#/runs/<id>?view=graph`, so a link carries
  it, and remembered in `localStorage` for the next run opened. One view at
  a time in the main area; the run's facts and the cancel control stay
  above either.
- Tests: the pure graph in step 2 carries the logic. For the component, jsdom
  lacks `ResizeObserver` and layout; stub `ResizeObserver` in
  `src/test/setup.ts` and assert on the nodes' text and count, not on
  positions. Pan and zoom are for the browser test.
- The CSS React Flow ships is imported once; it bundles into ours. Check the
  build's size and the bundled-package list after this step.

## Choices made while planning

- React Flow with dagre, not dagre alone: the reader asked for zooming and
  panning, which is what React Flow is; a static SVG would have saved 59 KB
  gzipped and 18 packages, and is the fallback if the graph disappoints.
- One node per step instance, in parent nodes per iteration or branch,
  rather than one node per step with the instances listed inside: the
  reader wants to see a run's shape, and the instances are the shape.
- The outline stays, as a second view, not beside the graph: one main area,
  a switch, the choice kept in the route and remembered.
- The look is taken from the screenshots as style and layout only. Columns
  the data does not have are dropped, not faked.
- The profile is a placeholder with nothing behind it. Authentication is a
  separate plan, and this one must not pretend otherwise.
- The screenshots stay in `tmp/`, which is not versioned; this plan
  describes them in words so the work does not depend on the files.
